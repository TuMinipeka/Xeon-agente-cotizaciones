# Persistencia operativa de XEON (D15 A)

XEON puede guardar el embudo, carrito, memoria conversacional, borradores, bandeja del asesor y los IDs de webhooks procesados en un PostgreSQL **propio de XEON**. Es independiente del `DATA_SOURCE=sql` de la ferretería: ese conector conserva sus consultas de solo lectura y su propio archivo de URL. El valor por defecto `STATE_STORE=memory` mantiene las pruebas sin red.

## Desarrollo local en cuatro pasos

1. Iniciar PostgreSQL 17 local: `docker compose -f compose.state.yaml up -d --wait`. El compose usa credenciales visibles **solo para desarrollo**, puerto local `55433` y volumen `xeon_state_data`. No usar estas credenciales en producción.
2. Crear `secrets/xeon_state_url.txt` (ignorado por Git) con la URL `postgresql+psycopg://xeon_dev:xeon-local-only@127.0.0.1:55433/xeon_state`. El archivo se lee en ejecución; no colocar la URL en YAML, variables de log ni `alembic.ini`.
3. Ejecutar `uv sync --locked --group db` y `uv run --locked --group db alembic upgrade head`. Alembic lee `XEON_STATE_URL_FILE`, cuyo valor predeterminado es `secrets/xeon_state_url.txt`.
4. Configurar `STATE_STORE=postgres` en el entorno del proceso XEON. `DATA_SOURCE` se configura por separado (`synthetic` o `sql`).

Para volver a memoria en desarrollo o pruebas, usar `STATE_STORE=memory`. `APP_ENV=production` exige `STATE_STORE=postgres` y falla al construir el contenedor si se selecciona memoria: la deduplicación en memoria no sobrevive a reinicios. Para detener el servicio local: `docker compose -f compose.state.yaml down`. `down -v` **elimina el volumen y todo el estado local**; usarlo únicamente en una base de pruebas desechable. Probar la reversión de esquema con `uv run --locked --group db alembic downgrade base` en una base desechable y volver a `upgrade head`.

## Garantías y límites

- Una transacción PostgreSQL y `pg_advisory_xact_lock` por clave de conversación serializan pasos del embudo en distintos workers. En ella se guardan embudo, carrito, memoria y borrador. El carrito además compara su versión y rechaza una escritura obsoleta.
- `processed_events` tiene clave primaria `(tenant_id, instance, message_id)`. El webhook toma la reclamación dentro de esa transacción, junto con la respuesta. Dos workers con el mismo ID generan un solo envío y un solo borrador. El repositorio de borradores tiene la restricción única `(tenant_id, request_id)`.
- La migración `0002_advisor_inbox` añade eventos del asesor con separación por tenant y deduplicación de pendientes. Una revisión humana bloquea el evento y el borrador en la misma transacción: dos asesores compitiendo por aprobar o rechazar reciben un éxito y un conflicto. Los borradores también se leen por tenant.
- Las sesiones del panel conservan solo la huella HMAC del token en memoria, con expiración. Reiniciar invalida los inicios de sesión y un despliegue con varios workers necesita afinidad para el panel; la bandeja y sus decisiones sí son compartidas. Esta elección evita persistir credenciales de sesión. La autenticación distribuida queda fuera del corte.
- La migración `0003_kapso_outbox` añade `inbound_deliveries` y `outbound_deliveries`. El webhook verifica la firma y valida el mensaje antes de guardar el evento v2 crudo en PostgreSQL; el acuse HTTP 200 ocurre después del commit. Si la escritura falla, devuelve error para que Kapso reintente. La cola ordena los mensajes pendientes por conversación, con una clave única `(tenant_id, instance, message_id)`.
- El receptor limita el cuerpo a 1 MiB: comprueba `Content-Length` y corta la lectura en streaming al excederlo, con HTTP 413. Admite hasta 100 eventos por lote (el máximo documentado por Kapso); un lote mayor devuelve 413. Si un evento del lote carece de `message.id`, deriva su id de `X-Idempotency-Key` más el índice, sin colapsar mensajes distintos. Cuando `KAPSO_PHONE_NUMBER_ID` está configurado, ignora eventos firmados de otro número y registra solo el motivo, sin teléfono ni texto. La [documentación oficial de cabeceras v2](https://docs.kapso.ai/docs/platform/webhooks/overview) no incluye una marca de tiempo firmada; `message.timestamp` no prueba la frescura de la entrega y no se usa para rechazar eventos antiguos.
- El trabajador procesa el mensaje, el estado del embudo y la respuesta saliente en una misma transacción. Para avisos del panel, la decisión humana y el envío saliente se registran juntos. Los envíos tienen clave única, estado `pending` (pendiente), `sent` (aceptado por Kapso) o `failed` (fallido definitivo), lease por trabajador y reintentos con backoff exponencial hasta cinco intentos. HTTP 4xx es definitivo salvo 408, 409, 425 y 429; errores de red y 5xx se reintentan. Los envíos al mismo destinatario conservan el orden mientras los anteriores sigan pendientes.
- **Garantía real: al menos una vez, no exactamente una vez.** La clave única evita que un webhook repetido cree dos respuestas locales. Si Kapso acepta el mensaje pero el proceso cae antes de guardar el acuse remoto, el lease vence y puede reenviarse. La [API documentada para enviar texto](https://docs.kapso.ai/docs/whatsapp/send-messages/text) y [botones](https://docs.kapso.ai/docs/whatsapp/send-messages/buttons) no documenta una clave de idempotencia de salida. El encabezado `X-Idempotency-Key` de la [documentación de webhooks](https://docs.kapso.ai/docs/platform/webhooks/overview) identifica **entregas entrantes**, no envíos. El estado `sent` significa aceptación por el proveedor, no entrega al teléfono.
- `STATE_STORE=memory` conserva el procesamiento y envío inmediato sin durabilidad. Con PostgreSQL, el worker corre en la API por defecto (`DELIVERY_WORKER_ENABLED=true`, `DELIVERY_POLL_SECONDS=0.5`). Para ejecutarlo aparte, configura `DELIVERY_WORKER_ENABLED=false` en la API y ejecuta `uv run --locked --group db python scripts/run_delivery_worker.py` con `STATE_STORE=postgres` y `WHATSAPP_SEND_ENABLED=true`. Detén el proceso con Ctrl+C; el lease de cualquier intento interrumpido caduca y otro trabajador lo retoma. Sin canal habilitado, la respuesta queda pendiente en la tabla. Los mensajes que agotan sus intentos permanecen como `failed` para atención operativa; no se borran solos.
- Los payloads de estado son `JSONB` con `schema_version=1` y serializadores explícitos. Un despliegue futuro que cambie su estructura debe migrar los datos antes de cambiar el lector. La memoria incluye texto del cliente y la dirección; proteger la base, el volumen, copias de seguridad y accesos de producción.
- **Retención de datos: POR DEFINIR por el usuario.** No hay limpieza automática ni plazo inferido. También quedan por definir cifrado en reposo, copias de seguridad y recuperación en producción.

## Verificación

La suite normal no necesita PostgreSQL. Para integración local, levantar además `docker compose -f compose.db-test.yaml up -d --wait` (conector D13), ejecutar `uv run --locked --group db --group db-test pytest -m integration` y apagar ambos servicios al terminar. `tests/integration/test_state_postgres.py` verifica reinicio, dos instancias, carrera del carrito, ingreso durable antes del acuse, recuperación del outbox tras reinicio, orden y backoff; `tests/test_delivery_worker.py` usa dobles HTTP. `tests/integration/test_sql_engines.py` comprueba el conector de ferretería por separado. Ninguna prueba invoca un LLM pagado ni envía mensajes reales.
